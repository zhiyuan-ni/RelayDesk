# RelayDesk

面向电商客服场景的多 Agent 编排服务：先识别意图，再路由给通用、技术、账单三类 Agent 或人工升级节点，Agent 通过受白名单约束的工具查询业务数据和知识库，回复经确定性检查与模型评委双重评测。

```
用户消息
  ├─ 读取会话记忆（Redis）           ─┐ 
  ├─ 意图识别（LLM + 规则双路融合）     │ 并行
  └─ 长期记忆召回（ChromaDB，时间衰减）─┘
        ↓
  路由决策：升级 / 澄清 / 主 Agent + 辅助 Agent
        ↓
  Agent 并行执行 ── tool-use 循环 ── 工具白名单 ── 订单 / 支付 / 退款 / 发票 / 登录记录 / 知识库检索
        ↓
  多 Agent 时合并回复 → 写入会话记忆 → 后台更新长期记忆
```

## 快速开始

需要一个 OpenAI 协议兼容的模型服务（项目开发时使用 aihubmix 中转）和 Docker。

```bash
cp .env.example .env        # 填入 LLM_API_KEY，其余按需修改
docker compose up -d --build
```

打开 http://localhost:8000/docs 。本地开发时只起 Redis，服务在宿主机运行：

```bash
docker compose up -d redis
uv sync
uv run uvicorn app.main:app --reload
```

试一试，注意第一次请求返回的 `conv_id` 要在后续请求里带上：

```bash
curl -s localhost:8000/chat -H 'Content-Type: application/json' \
  -d '{"message": "订单 B20250917 为什么扣了我两次钱", "user_id": "u1001"}'
```

返回里除了回复，还有意图、路由分数与理由、实际参与的 Agent、每次工具调用的参数与结果、想起的长期记忆，以及各环节耗时。

## 接口

| 接口 | 作用 |
|---|---|
| `POST /chat` | 主入口 |
| `POST /search` | 知识库检索，`enhanced=false` 可对比纯向量检索 |
| `GET /metrics` | 各环节、各 Agent、各工具最近 500 次的调用量、成功率、P50/P95/P99 延迟 |
| `GET /health` | 健康检查 |

## 评测

所有数字都由仓库里的脚本产生，报告在 `evals/reports/`。

```bash
uv run python scripts/eval_intent.py --split test   # 意图识别与路由
uv run python scripts/eval_e2e.py                   # 端到端场景 + 模型评委
uv run python scripts/compare_retrieval.py          # 检索三种模式对比
```

| 指标 | 结果 | 说明 |
|---|---|---|
| 意图识别准确率 | 91.2%，95% 置信区间 86.5% 到 94.4% | 测试集 205 条，与开发集按文本哈希固定划分，提示词只在开发集上迭代 |
| 意图识别宏平均 F1 | 0.919 | 同上 |
| 路由准确率 | 93.2% | 识别结果送入真实路由函数，主 Agent 选对的比例 |
| 意图说明的作用 | 开发集 80.5% → 93.2% | 提示词中逐条界定意图边界前后的对比 |
| 意图分类换用 jev | 测试集 91.2% → 90.7%，单次调用中位数约 3.0 秒 → 0.5 秒 | `INTENT_BACKEND=jev`。准确率差距在置信区间内；jev 置信度 ≥0.9 的样本占 75%、准确率 98.7%，LLM 自报置信度全部 ≥0.9，没有区分度 |
| 端到端确定性检查 | 11 轮全部通过 | 9 个场景：重复扣款、复合问题、多轮退款、账号安全、转人工、澄清、政策检索、越权查询、编造订单号 |
| 模型评委评分 | 事实 4.8 到 5.0，有帮助 4.8，边界 5.0，满分 5 | 评委为另一厂商模型，对照事实清单打分，只做辅助指标 |
| 知识库首位命中率 | 纯向量 73% → 加重排 100% | 15 条避开文档原词的问法 |
| 重排换用 jev | 首位命中率同为 100%，重排一步约 1.0 秒 → 0.6 秒 | `RERANK_BACKEND=jev`。每个候选一道是非题，一次请求问完，按"是"的概率排序 |
| 端到端延迟中位数 | 10.1 秒 → 5.4 到 8.6 秒 | 限制回复长度、重排换小模型；中转站延迟波动大，取多次运行的范围 |

评测集 338 条，其中 298 条原话取自公开数据集 CSDS（Lin et al., EMNLP 2021，基于京东客服对话），全部按本项目的 11 类意图重新标注，标注规则见 `evals/ANNOTATION_GUIDE.md`。

## 主要设计决策

- **提示词管不住的事情用代码兜住。** 工具白名单、订单归属校验、只查当前用户的登录记录、订单号必须是用户亲口说过的、会话键带用户 ID。四处都是同一个原则：客户端和模型给的标识符都不可信。
- **人工升级节点不调用模型。** 用户要求转人工时，模板回复零延迟，也杜绝模型"安慰性地"声称已经处理了什么。
- **端到端检查写不变量，不写轨迹。** 检查"两个 Agent 都参与、金额和错误码都出现、没有承诺退款"，不规定先调哪个工具、用哪个词。模型每次走的路径可以不同。
- **用数据决定功能去留。** 查询改写在当前知识库上没有收益，默认关闭；意图分类试用小模型，开发集看似无损，测试集掉 4 个点，保留主模型。两个决定都有报告可查。
- **只做选择的环节交给分类模型。** 意图分类是从 11 类里选一个，重排是判断每个片段能否回答问题，两者都可切换为 TypeSafe 的 jev（`INTENT_BACKEND`、`RERANK_BACKEND`）。返回值必然落在题目定义的范围内，省掉解析和校验模型输出的代码；意图的置信度经过校准，融合函数里的阈值才真正起作用。重排把全部候选放进一次请求，每道题只带自己的片段，逐对打分但只有一次往返。jev 读题很字面，边界规则写进每个选项的说明，与 LLM 提示词共用同一份意图说明。
- **失败分两类处理。** 配置错误（模型名不存在、密钥失效）启动即失败；暂时不可用（网络、限流）在本地数据可用时降级启动，运行期靠超时、熔断、缓存和降级文案兜底。

## 目录

```
app/
  intent/         意图识别：规则路、LLM 路、融合
  routing/        路由打分与决策
  agents/         Agent 基类与 tool-use 循环、角色设定、工具、升级节点
  knowledge/      文档切片、向量库、检索器（召回、改写、重排）、检索工具
  memory/         会话记忆（Redis）、对话压缩、长期记忆（ChromaDB）
  reliability/    TTL 缓存、熔断器、工具保护
  observability/  请求时间线、统计
  evals/          分类指标、端到端检查、模型评委
  business/       模拟业务数据与查询
evals/            评测集、标注指南、场景、报告
scripts/          评测与对比脚本、候选样本抽取
tests/            178 个单元测试，不联网、不依赖 Redis
```

## 已知局限

- 业务数据是模拟的 JSON，真实系统里替换 `app/business/store.py` 即可，工具和 Agent 不用改。
- 知识库检索的缓存按精确字符串命中，模型生成的检索语句措辞略有不同就无法命中。
- 长期记忆的时间衰减假设"越近越相关"，用户明确问几个月前的事时会吃亏。
- 评测集没有真实线上流量，上线后应从转人工和低置信度的对话里滚动补充。
- 中转站延迟波动大，所有延迟数字都应看作范围而不是精确值。
