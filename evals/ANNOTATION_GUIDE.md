# 意图标注指南

这份文档记录评测集是怎么标的。标注过程中遇到的每一个拿不准的案例，都要在这里写下判断和理由。
同一类问题以后再出现，按这里的规则标，保证前后一致。

## 数据格式

`evals/intent_cases.jsonl`，每行一条 JSON：

```json
{"text": "用户的原话", "intent": "refund"}
{"text": "A12345", "intent": "refund", "history": [{"role": "user", "content": "我想退款"}], "note": "省略句"}
```

- `text` 和 `intent` 必填。`intent` 只能是下面 11 个值之一。
- `history` 选填，用于需要上文才能判断的省略句。
- `note` 选填，记录这条样本的特殊之处，比如"边界案例，见指南第 3 条"。

## 11 个意图的定义

| 意图 | 定义 | 不包括 |
|---|---|---|
| greeting | 打招呼、确认是否有人 | 带具体问题的开场白，按具体问题标 |
| order_logistics | 订单状态、发货、物流进度、改地址、取消或拦截订单、拒收 | 取消或拒收之后问退款，标 refund |
| complaint | 表达不满，没有提出具体业务诉求 | 带着不满情绪提出具体诉求的，按诉求标 |
| refund | 售后类：退货、换货、维修保修、少件错发要求补发、退款申请、退款进度。名字沿用 refund | 被多扣钱要求退回，标 payment_issue；只问物流到哪了，标 order_logistics |
| invoice | 开票、改抬头、发票进度 | |
| payment_issue | 重复扣款、支付失败、扣款金额不对、钱已经付了但充值或权益没到账 | 退款没到账，标 refund；付款之前问支持哪些支付方式，标 other |
| tech_login | 登录不上、忘记密码、收不到验证码、登录报错 | 账号疑似被盗，标 account_security；绑定的手机号已换或停用，要先改绑才能登录的，标 account_security |
| tech_error | 闪退、白屏、页面报错、按钮点不了、提交不了、一直加载 | 因为业务状态不允许而做不了的（没货、限购、订单未完成不能申请售后），按对应业务标或标 other |
| account_security | 被盗、异常登录、改登录密码或支付密码、改绑手机或邮箱、解绑、实名认证、注销 | |
| human_handoff | 明确要求人工或真人、问有没有人工、要客服电话或热线、要找某个客服 | 要快递员、站点、商家的电话，按对应业务标；句子里有"人工"但诉求是别的，按诉求标 |
| other | 和客服业务无关，或者无法判断 | |

## 每类的数量目标

总数 300 到 350 条。数据充足的类（order_logistics、refund、invoice、account_security、human_handoff、other）每类 30 到 35 条，数据少的类（payment_issue、tech_login、tech_error、complaint）每类 20 条左右，greeting 15 条就够，它太简单，多了只会抬高总准确率。任何一类都不要少于 15 条。

为什么是这个规模：总体准确率在 90% 附近时，130 条的 95% 置信区间是正负 5 个点，330 条是正负 3 个点；每类 10 条时错一条召回率就掉 10 个点，每类 30 条时是 3 个点。另外样本要分成开发集和测试集（见 `scripts/eval_intent.py --split`），调参数只看开发集，130 条分不开。

数量不能拿标签质量换。每一条的 `intent` 都必须是自己看过原话后的判断，`scripts/build_intent_candidates.py` 给的建议意图只是起点。

每一类里建议包含：

- 一半左右是**不含明显关键词**的口语说法。"我要退款"这种太简单，测不出区别。
- 两三条**边界案例**，也就是你自己标的时候都要想一下的。
- 一两条带 `history` 的省略句。

## 边界案例的判断规则

标注时遇到拿不准的，在这里新增一条，写清楚怎么判、为什么。下面两条是示例，请改成你自己的判断。

1. **带情绪的具体诉求**，例如"等了一周还不发货，你们怎么回事"。
   判断：标 `order_logistics`。理由：用户有明确的业务问题，处理它比安抚情绪更要紧。

2. **"我的钱呢"这类信息不足的话**。
   判断：待定。

3. **换货、维修、保修、补发**，例如"用了两天就坏了能换吗""少发了一个配件"。
   判断：标 `refund`。理由：`refund` 的范围在 2026-09-21 扩成了整个售后类。依据是 CSDS 数据集一万段真实电商客服对话的统计，退换修约占 18.7%，退款约占 4.7%，原先的定义只接住了后者。这些诉求由同一个 Agent 处理，拆成两类不会改变系统行为。

4. **售前咨询、价保优惠、安装预约**，例如"这款有没有蓝色""买贵了能补差价吗"。
   判断：标 `other`。理由：同一份统计里它们合计约占 19%，但系统没有对应的业务数据和工具，识别出来也无法处理。如果评测显示 `other` 成了错例的集中去向，再考虑拆分。

5. **话费、流量、游戏币等充值，钱付了但没到账**，例如"早上充的话费怎么还没到""充了半小时了还没到账"。
   判断：标 `payment_issue`。理由：钱已经被扣走而用户没有拿到对应的东西，处理动作是查支付流水确认这笔钱的状态，和重复扣款、支付失败走的是同一个 Agent、同一个工具。已经付款后问"一般多久到账"也按这一条标，因为用户关心的仍然是自己这笔钱。
   不适用的情况：还没付款，只是问能不能充、支持哪些支付方式，标 `other`；退款没到账标 `refund`。

6. **取消订单**，例如"我新下的订单怎么取消""不能拦截物流吗"。
   判断：还没收到货，想取消、拦截、改单的，标 `order_logistics`。理由：处理动作是查订单状态、拦截发货，和退货流程无关。取消之后问钱什么时候退、退到哪的，标 `refund`。

7. **拒收**，例如"拒收后还要什么操作吗""不想退了可以直接签收吧"。
   判断：问能不能拒收、拒收怎么操作的，标 `order_logistics`，同第 6 条的理由。拒收之后问退款的，标 `refund`。"拒收了怎么还扣款"这种字面像支付问题的，实际诉求是拒收后的退款，标 `refund`。

8. **支付密码的修改、找回**，例如"支付密码忘了能找回吗"。
   判断：标 `account_security`。理由：处理动作是核验身份后重置凭证，和改登录密码是同一套流程，和查支付流水无关。

9. **手机号换了导致登不上**，例如"绑定的手机号不用了，登录要验证短信怎么办"。
   判断：只说忘记密码、收不到验证码的，标 `tech_login`；明确说绑定的手机号已经换了或停用、需要改绑才能解决的，标 `account_security`。理由：前者是登录环节的故障排查，后者必须先改绑，而改绑要走身份核验。

10. **和"人工"沾边的说法**，例如"人工电话多少""要人工申请一下价保""快递员电话给我"。
    判断：要转人工、问有没有真人、要客服电话或热线、要找某个客服的，标 `human_handoff`，因为用户要的是一个人来接手。要快递员、站点、商家电话的，标 `order_logistics`，用户要的是配送环节的联系方式。"人工"只是顺口带上、诉求另有所指的，按诉求标。

11. **"提交不了""下不了单"这类做不了某个操作的话**。
    判断：页面上的操作本身失败（按钮点不了、提交报错、一直加载、显示的状态明显不对），标 `tech_error`，不管做的是哪项业务，因为处理动作是排查故障。因为业务规则或状态不允许（没货、限购、订单没完成不能申请售后、券没到有效期）而做不了的，按对应业务标或标 `other`，因为处理动作是解释规则。从原话分不出是哪种的，不要收进评测集。

## 样本来源

评测集里的样本分三种来源，由 `author` 字段区分：

- 没有 `author` 字段的是自己写的。
- `seed` 是搭建评测框架时写的 12 条初始样本。
- `csds` 的原话取自公开数据集 CSDS，由 `scripts/build_intent_candidates.py` 抽取候选，再逐条人工确认。数据集自带的 211 类标签没有使用，意图全部按本指南重新标注。

### CSDS 数据集说明

- 论文：Lin et al., *CSDS: A Fine-Grained Chinese Dataset for Customer Service Dialogue Summarization*, EMNLP 2021。https://aclanthology.org/2021.emnlp-main.365
- 仓库：https://github.com/xiaolinAndy/CSDS
- 数据本身来自京东客服对话语料 JDDC，由论文作者做了脱敏和标注，用于学术研究。
- 截至 2026-09-23，该仓库没有附带许可证文件，也没有写明使用条款。本项目按学术数据集的惯例处理：
  原始数据文件不进仓库（`dataset/` 已在 `.gitignore` 里）；仓库里只保留 298 条经过挑选和重新标注的用户单句，
  不含商家回复和对话上下文以外的内容；仅用于本项目的非商业评测。如数据集作者对此有异议，这部分样本会立即移除。
- 使用时请引用上述论文。

## 写样本时的注意事项

- 不要照抄 `app/intent/llm_classifier.py` 里 few-shot 的句子，评测脚本会检查并报错。原因是那些句子的答案已经写在提示词里了，拿来测等于开卷考试。
- 不要看着关键词表 `app/intent/rules.py` 来造句。真实用户不知道关键词表。
- 长短搭配，加入错别字、口语、中英混杂、没有标点的句子，真实用户就是这么打字的。
- 标完一批就跑一次评测，看错例。错例分两种：系统错了，或者你标错了。后一种比想象的常见。
